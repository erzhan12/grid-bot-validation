# Feature 0104 — Improve cancel failure handling and emergency-cancel alerting

## Context

`BybitRestClient.cancel_order()` currently returns bare `False` for benign terminal-order races, unexpected Bybit responses, auth errors, and transport exceptions. This makes the serious-failure branch indistinguishable from “the order is already gone.”

The auth-cooldown bypass is provable: `rest_client.py:571-575` catches network/auth exceptions and returns `False`, so `IntentExecutor.execute_cancel()` follows its warning-only `success=False` branch. Its `except Exception` branch—which calls `_handle_error()`, classifies the error, records REST health metrics, and can activate auth cooldown—is unreachable for those real adapter failures.

Pybit sharpens the required adapter behavior:

- Non-zero Bybit `retCode` values normally raise `pybit.exceptions.InvalidRequestError` before `cancel_order()` receives a response dict. Its `status_code` and `message` attributes must therefore be classified alongside explicit mocked response dictionaries.
- With pybit’s existing `force_retry=False`, connection/read-timeout exceptions propagate directly from the HTTP layer.
- `FailedRequestError` and other non-benign exceptions must remain serious.

Issue #208 requires, verbatim:

- Cancel failures carry retCode/retMsg or exception info.
- Auth-related cancel failures trigger auth cooldown.
- Loss-breaker cancel failure emits an alert with strategy/order identifiers.
- Tests: successful cancel; non-zero retCode; network exception; auth exception; loss-breaker cancel failure alerting.

## Cancellation outcome contract

Add a frozen, fully typed `CancelOrderResult` dataclass in `packages/bybit_adapter/src/bybit_adapter/rest_client.py` with:

- `success: bool`
- `benign: bool`
- `ret_code: int | None`
- `ret_msg: str | None`
- `exception: Exception | None`

This type belongs in `bybit_adapter` because `retCode`, `retMsg`, and pybit exceptions are exchange-transport details. `gridcore` remains dependency-free. `gridcore.intents.CancelIntent` is unchanged; the existing `CancelResult` is actually defined in `apps/gridbot/src/gridbot/executor.py`, not in `gridcore`.

Do not add `retryable` or `auth_error` fields. Those decisions belong to the existing executor classifiers; storing them in the adapter would introduce a parallel classification system contrary to `.claude/rules/code-style.md`.

Outcome handling must be:

| Adapter outcome | `CancelOrderResult` | Executor escalation |
|---|---|---|
| `retCode == 0` | `success=True`, `benign=False`, retain code/message | Reset auth-failure count; record successful cancel |
| Code `110001`, `110008`, `110010`, or `170213` | `success=False`, `benign=True`, retain code/message and any pybit exception | No `_handle_error()`, auth cooldown, REST-error metric, reject metric, or alert |
| Message contains `not found`, `not exist`, `already filled`, `already cancelled`, `has been cancelled`, or `completed or cancelled` | Same benign result, including when surfaced through `InvalidRequestError` | Same quiet handling |
| Unexpected non-zero response | `success=False`, `benign=False`, retain `retCode`/`retMsg` | Format the established `[retCode] retMsg` error, then call `_handle_error()` |
| Unexpected `InvalidRequestError`, `FailedRequestError`, or transport exception | `success=False`, `benign=False`, retain exception and available code/message | Use `str(exception)`, then call `_handle_error()` |

### The benign catalog itself must be corrected first

`_EXPECTED_CANCEL_CODES` is currently `{110001, 110003, 170213}` (`rest_client.py:569`). Verified against the
official V5 table (<https://bybit-exchange.github.io/docs/v5/error>, the reference `error_codes.py:8` already
names), that set is wrong in both directions:

- `110003` = "Order price exceeds the allowable range." That is an order-*placement* price error, not a
  terminal-order condition. It cannot arise from a cancel request, which carries no price. **Remove it** —
  keeping it would mean silently swallowing a genuinely unexpected response as "order already gone".
- `110008` = "The order has been completed or cancelled." and `110010` = "The order has been cancelled."
  Both are the real terminal-order responses for a linear cancel, and both are **missing**. **Add them.**

This correction is not optional polish — it is load-bearing for this feature. Today every one of these codes
collapses to the same bare `False`, so the catalog's contents are inert. The moment benign and serious
diverge, an uncatalogued `110008`/`110010` becomes a *serious* failure on an ordinary fill-vs-cancel race:
it fires the emergency alert and bumps `rest_errors_by_code["other"]`. It does NOT latch auth cooldown —
`_handle_error()` gates the cooldown on `_is_auth_error()` (`executor.py:285-297`) — but it takes the `else`
branch that RESETS `_auth_failure_count` to zero (`executor.py:297-298`), so a stream of misclassified
terminal-order races would repeatedly clear a genuinely accumulating auth-failure count and delay a real
cooldown. False alerts plus a suppressed auth signal is precisely what the outcome contract above exists to
prevent.

`170213` stays in the set. It is documented under Spot Trade while `cancel_order()` hardcodes
`category="linear"` (`rest_client.py:558`), so it is unreachable here — but it is pre-existing, its meaning
("Order does not exist") is benign anyway, so its presence cannot cause a misclassification, and
`.claude/rules/code-style.md` says to leave pre-existing dead entries in place and mention them rather than
delete them. Contrast `110003`, which is removed not because it is unreachable but because it is actively
WRONG: it means a price-range rejection, so classifying it benign would swallow a real anomaly.

The pre-existing message fallback does NOT save us: the documented wordings are "The order has been completed
or cancelled." and "The order has been cancelled", neither of which contains the existing `already cancelled`
phrase. Hence both the code additions AND the two extra fallback phrases in the table above.

Because those two new phrases DO match the documented wordings, the fallback and the catalog now overlap for
exactly these codes. That overlap is deliberate defence-in-depth, but it means a test using the real `retMsg`
can no longer distinguish "classified by code" from "classified by phrase" — see the empty-`retMsg`
parametrization mandated in Phase 1 RED, which is what actually pins the catalog.

Additionally, restrict the message fallback so it cannot fire for five-digit `10xxx` system/routing codes.
`10017` = "Route not found." and `10404` = "op type is not found" both contain the pre-existing `not found`
phrase, yet neither means "the order is already gone" — a misrouted or misconfigured cancel would otherwise be
classified benign and pass silently, which is the precise failure this feature exists to eliminate. The
fallback's remaining job is to catch NEW, uncatalogued *order-scoped* terminal codes, so scoping it to the
six-digit `110xxx`/`170xxx` order ranges is both narrower and more correct.

`IntentExecutor.execute_cancel()` continues returning its existing `CancelResult`. Serious adapter failures populate `CancelResult.error`; benign outcomes return `success=False` with `error=None`. This preserves the externally useful distinction without moving exchange details into `gridcore`.

Health accounting remains schema-compatible:

- Successful cancellation increments `metrics.cancels`.
- Benign and serious unsuccessful attempts increment `metrics.cancels_failed`.
- Serious failures call `_handle_error()` exactly once, incrementing `metrics.rest_errors_by_code` through the existing `_classify_error()` and module-level classifier functions: `auth`, `network`, or `other` for an otherwise-unclassified unexpected code.
- Benign failures do not increment `rest_errors_by_code`.
- Do not call `record_reject()` for cancellations; `orders_rejected` describes placement rejection, while `cancels_failed` already represents cancellation failures.
- Do not add a counter or change `HealthMetrics.as_dict()` or the feature-0082 status-file JSON schema.

## CancelIntent-producing paths and alert scope

| Producer and dispatch path | Reasons | Failure policy |
|---|---|---|
| `GridEngine._check_and_place()` and `_place_grid_orders()`, dispatched from `StrategyRunner.on_ticker()` through `_execute_generated_intents()` / `_execute_intents()` | `rebuild`, `duplicate`, `side_mismatch`, `outside_grid` | Routine grid churn. | `StrategyRunner._enter_chase()` and `_retire_live_chase_order()`, buffered until `_drain_pending_chase_intents()` | `chase_close`, `chase_replace`, `chase_exit` | Active-defense maintenance, but not the issue’s emergency path. Apply the same routine policy. |

### Emergency alert must be aggregated, not per-order

`Notifier.alert()` throttles to one delivery per `error_key` per 60 seconds. A per-order alert inside the
cancel loop would therefore deliver only the FIRST failure and silently drop the rest — the operator would
learn that "an" emergency cancel failed while N-1 still-live orders went unnamed. `_evaluate_loss_breaker()`
must instead accumulate the seriously-failed cancellations across the loop and emit a single alert after it:

- Message: `Gridbot: EMERGENCY loss-breaker cancel FAILED for {strat_id}: {failed_count + skipped_count} of {total_count} working orders still live ({failed_count} failed, {skipped_count} not attempted — auth cooldown); order_ids={comma_separated_failed_and_skipped_order_ids}; first_error={error}`
- `error_key`: `safety_cap_loss_breaker_cancel_failed_{strat_id}`

The `order_ids` list MUST be bounded. Wire order ids are ~30 characters (16-hex prefix + `-` + 13-digit
millis), a grid can legitimately carry many working orders, and Telegram's `sendMessage` rejects payloads over
4096 characters — after which `Notifier._send_telegram()` only logs the failure while the throttle key stays
marked as sent, so the operator gets NOTHING for the next 60 seconds. Render at most the first 20 ids
followed by `(+N more)`, and keep the counts (which are what the operator acts on) ahead of the id list in the
message so a truncation can never cost the tally. Cap `first_error` at 500 characters for the same reason —
it is interpolated unbounded, and `str(FailedRequestError)` embeds the full `\nRequest → {request}` tail
(`pybit/exceptions.py`), so it is the other input that can grow without limit. Cover BOTH with tests: a
large-sweep test asserting the rendered length stays under 4096, and a long-`first_error` test asserting the
same. Length must be bounded by construction, not by luck, because `Notifier.alert()` marks the throttle key
before `_send_telegram()` runs and a rejected send is only logged — an over-length alert is silently lost for
the next 60 seconds.

The still-live count is `failed_count + skipped_count`, NOT `total_count`: cancels that succeeded earlier in
the sweep are no longer live and must not be reported as such. When the sweep produced no failures at all —
possible when auth cooldown was ALREADY latched before `_evaluate_loss_breaker()` ran, so the loop breaks on
its first iteration and every order is skipped — there is no failure to source `first_error` from; emit
`first_error=none (auth cooldown already active)` in that case rather than an empty or `None` value.

The key includes `strat_id` and is distinct from the trip alert’s `safety_cap_loss_breaker_{strat_id}`, so
the two do not throttle each other. Each individual serious failure is additionally logged at ERROR inside
the loop (so the full per-order detail survives in the log even when a later sweep is throttled). The
`skipped_count` term is load-bearing: with the auth-cooldown break below, orders that were never attempted
are just as live as ones that failed, and the operator needs the true still-live total.

### Retry-queue and cooldown behavior in the emergency path

Four behavioral decisions, each a direct consequence of finally having the benign/serious signal. None is a
speculative extra: without them the plan's own "benign stays quiet" policy is not actually implemented.

- **Benign cancel results must NOT enqueue a retry.** Today `_execute_cancel_intent()`
  (`runner.py:2522-2523`) fires `_on_intent_failed` for every unsuccessful cancel, and
  `orchestrator.py:966` binds that to `retry_queue.add`. Because `RetryQueue.process_due()` only drops
  entries on a `result.error` matching a known sentinel (`retry_queue.py:231-236`), an `error=None` benign
  result falls to the generic backoff branch and is re-cancelled up to 3 times — three REST round-trips that
  can only ever return "order not found" again, each bumping `cancels_failed`. Gate the callback on
  `result.error is not None` so only serious failures enqueue. This is safe because, per the outcome
  contract above, every serious result populates `error` and every benign result leaves it `None`. Note the
  gate must live on the cancel path only; `PlaceLimitIntent` failures keep their existing behavior.
- **A retry whose cancel resolves benign must be dropped, not re-backed-off.** Gating the initial enqueue is
  not sufficient. A legitimately-enqueued SERIOUS cancel commonly resolves benign on a later attempt — the
  order filled or was cancelled in the meantime. That outcome carries `error=None`, so it misses the
  sentinel-drop branch (which requires a non-`None` error, `retry_queue.py:231-236`), falls into the generic
  backoff branch, is logged as `Unknown error` (`retry_queue.py:263-271`), and burns the remaining attempts
  on REST calls that can only return the same thing — the exact churn this feature exists to remove, just one
  step later. Add a drop branch to `process_due()` for an unsuccessful `CancelIntent` result carrying no
  error, mirroring the existing sentinel-drop treatment (`items_to_remove.append(item)`, `processed += 1`,
  log with a `benign cancel` reason at **INFO**). INFO rather than WARNING: `.claude/rules/code-style.md`
  reserves WARNING for "recoverable/divergence", and a retry resolving benign is the ordinary resolution of a
  fill-vs-cancel race. Logging it at WARNING would make it the loudest routine line in the log — recreating
  in the retry path exactly the noise this feature removes from the cancel path.
- **Loss-breaker cancel failures must NOT enqueue at all.** `RetryQueue` is constructed with
  `is_paused=lambda: (executor.auth_cooldown or safety_caps.loss_tripped())`
  (`orchestrator.py:918-920`) and `process_due()` returns 0 while paused (`retry_queue.py:185-186`).
  `loss_tripped()` stays latched for the rest of the session in the normal case — and `_evaluate_loss_breaker()`
  calls `_on_retry_queue_clear()` immediately before its cancel loop. An entry added during that loop is
  therefore either dead (exhausted by the queue's 30s `max_elapsed_seconds` guard, `retry_queue.py:205-212`,
  long before the latch could lift) or, in the narrow case where C3 trips within 30s of UTC midnight and
  `session_loss_auto_reset_utc_midnight` clears the latch (`safety_caps.py:139-152`), an unowned re-dispatch
  of a stale emergency cancel. Neither is useful; both misrepresent the state as "retry pending".
  Suppress the enqueue for the loss-breaker's own cancels and let the aggregated alert be the single, honest
  remediation signal. Do NOT instead relax `is_paused` to let cancels through the latch: that same predicate
  also covers `auth_cooldown`, so relaxing it would resume REST cancel traffic during a credential outage —
  a regression.
- **The loss-breaker cancel loop must break when auth cooldown latches.** `_execute_intents()` already does
  exactly this mid-batch (`runner.py:1276-1279`); the loss-breaker loop (`runner.py:2620-2629`) does not.
  This only becomes reachable once cancels start incrementing the auth-failure counter, which this feature
  introduces. Continuing to dispatch after cooldown latches is futile — the credentials are known bad, every
  remaining call fails, and each one inflates `cancels_failed` and `rest_errors_by_code`. Break out of the
  loop and count the unattempted orders into the alert's `skipped_count`, matching the established
  `_execute_intents()` precedent.

**Deliberately unchanged:** a benign cancel still does NOT mark the tracked order terminal
(`runner.py:2506` gates on `result.success`). Marking it terminal on a benign result would alter the
grid-state lifecycle that features 0031/0046/0087 depend on, which is outside the scope of issue #208.
Removing the benign enqueue (above) does not regress this: the retries it removes never marked the tracked
order terminal either.
