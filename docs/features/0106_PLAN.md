# Feature 0106 — Stale ticker age guard before order placement

## Context

`Orchestrator._on_ticker()` stores the latest normalized event per symbol in `_latest_ticker` (`apps/gridbot/src/gridbot/orchestrator.py:1105-1124`). Nothing anywhere checks how old that entry is — `grep` for `ticker_age` / `max_ticker` across `apps/gridbot/src` and `packages/gridcore/src` returns zero hits. The ticker drain in `_tick()` (`orchestrator.py:607-614`) only de-duplicates by object identity (`event is self._last_processed_ticker.get(symbol)`), which answers "have I already processed this object", not "is this price still valid".

When the public socket stalls or resets, the cache keeps its last entry and the bot keeps treating that price as current. `TickerEvent` already carries both `exchange_ts` and `local_ts` through its frozen base (`packages/gridcore/src/gridcore/events.py:33-36`); neither is read.

This feature blocks **live order submission** on a stale ticker, reports ticker age in the health snapshot, and keeps shadow mode logging the placement it would have made.

## Scoping decision (load-bearing — do not re-expand)

An earlier draft of this plan also rerouted the two *position-update* price consumers (the WS position drain at `orchestrator.py:580-586` and `PositionFetcher._fetch_one_account`) to pass `last_close=None` when the ticker is stale. **That is cut**, for three independent reasons:

1. **It would silence the per-tick heartbeat.** With a position open, `last_close=None` takes the early return at `runner.py:1042-1049`, which sits *before* the `"Position update - ratio=…"` INFO log at `runner.py:1092`. That line is the health analyzer's cadence/latency/liveness anchor. The rerouting would therefore kill the heartbeat precisely during a market-data outage — when monitoring matters most — and the project rule is explicit that this heartbeat stays.
2. **The claimed "partial update" is not what the code does.** The early return is gated on `has_position and not has_valid_price` (`runner.py:1042`). With a **flat** book it does not fire at all: execution continues with `price = 0.0`. It also skips the `_low_balance` refresh at `runner.py:1062`, which the draft did not mention.
3. **No acceptance criterion requires it.** All four criteria are satisfied by gating submission, reporting age, and logging in shadow mode.

Cutting it also brings the change to 3 production files, satisfying the ">3 files → split the task" rule in `.claude/rules/code-style.md`.

Consequence, accepted and documented: while the ticker is stale, risk multipliers keep updating from the last known price. That is safe here **because submission itself is blocked** — a stale multiplier cannot reach the exchange.

## Files and functions to change

- `apps/gridbot/src/gridbot/config.py` — add `max_ticker_age_seconds` to `StrategyConfig`.
- `apps/gridbot/src/gridbot/runner.py` — freshness assessment + the placement gate + the alert latch.
- `apps/gridbot/src/gridbot/orchestrator.py` — inject the ticker provider into the runner at `_init_strategy`, and report age / degrade health in `_write_health_snapshot`.

Explicitly NOT changed: `position_fetcher.py`, `_runner_market_price` (`orchestrator.py:84-91`), the WS position drain, `health.py`'s `HealthMetrics` counters, `TickerEvent`, the normalizer, `IntentExecutor`, the WS clients, `retry_queue.py`.

## Config

`max_ticker_age_seconds: float` on `StrategyConfig`, default **15.0**, declared `gt=0` **and** with a finite upper bound (`le=300.0`).

The upper bound is not decoration: the installed Pydantic accepts `float("inf")` under a bare `gt=0`, which would silently mark every ticker fresh forever and disable the guard. The repo already does exactly this elsewhere for the same reason — see `early_imbalance_multiplier` (`config.py:131-136`), whose `le=100.0` carries the comment "Upper bound 100 also rejects float('inf') from misconfigured YAML". Follow that precedent, including the rationale in the field description.

Per strategy, not global: ticker cadence differs by symbol, and this sits beside the other per-strategy risk controls. It is read on a live path, so it is not a dead field.

**On the default.** 15s, not the 5s the issue suggested. Do NOT justify it by the 30s public message-gap watchdog: that watchdog's `last_message_ts` is refreshed by *any* public message including public trades (`packages/bybit_adapter/src/bybit_adapter/ws_client.py:223-232, 283-323`), so trade traffic can keep the socket "alive" while ticker data is stale — the two are not comparable clocks. The real trade-off: too tight halts trading on legitimately quiet symbols; too loose lets orders out on materially old prices. 15s is deliberately conservative for a first ship on a live mainnet account and is meant to be tightened once the health snapshot has reported real age distributions.

## Freshness algorithm

Basis is **`local_ts`**, not `exchange_ts`. `local_ts` is stamped on receipt (`packages/bybit_adapter/src/bybit_adapter/normalizer.py:81-96`) and answers "how long since this process heard anything", which is the actual safety question. `exchange_ts` additionally carries exchange-vs-host clock disagreement, which is a real phenomenon here — the health analyzer has a dedicated `clock_drift` error category.

Three states (not four — see below):

- `fresh` — an event exists and `age <= max_ticker_age_seconds`.
- `stale` — an event exists and `age > max_ticker_age_seconds`.
- `no_data` — no ticker has ever reached the cache.

Do **not** add an `invalid` state for "`local_ts` missing or not a datetime": `Event.local_ts` is a typed field on a frozen dataclass and the normalizer always stamps `datetime.now(UTC)`, so that input is unreachable. Adding a sentinel, a health status and tests for it violates "no error handling for impossible scenarios". The one *reachable* clock anomaly is a host clock step-back producing a future `local_ts`; clamp negative ages to zero and treat them as `fresh`. Name the tolerance as a module constant rather than inlining a magic number.

Normalize naive timestamps as UTC the same way `_ensure_utc_aware()` does (`orchestrator.py:77-81`), and read "now" once per assessment. That helper is a module-private function of `orchestrator.py` while this assessment lives in `runner.py` — so this is a small re-implementation, NOT reuse. Do not import the private symbol across modules. Note this normalization is **test-fixture tolerance, not production handling**: the normalizer always stamps an aware `datetime.now(UTC)`, so production never supplies a naive value. It exists so hand-built fixtures cannot raise on aware/naive subtraction. Do not let it grow into a production-error branch — that is the same reasoning that deleted the `invalid` state above.

**Clock injection — naming.** `StrategyRunner.__init__` already takes a `clock` parameter, and it is **monotonic** (`runner.py:225`, `:315` — `clock or time.monotonic`). Do not overload it. Add a separately named optional wall-clock parameter (e.g. `utc_now`, defaulting to `lambda: datetime.now(UTC)`) so age math can never accidentally run against the monotonic clock.

**Provider injection.** The runner receives an optional zero-I/O callable returning the current cache entry for its symbol, bound in `_init_strategy` to `_latest_ticker[symbol]`. A runner constructed **without** a provider keeps today's behavior and applies no guard (preserves direct-test and tooling construction). A configured provider returning `None` means a real live `no_data`, not "guard disabled".

## Placement gate

The runner has exactly two production submission paths: `_execute_place_intent()` and `retry_dispatch_place()` (`runner.py:2238-2348`, `:2438-2500`; orchestrator retry dispatch routes place retries to the latter). Gate both.

- Assess freshness **after** quantity resolution but **before** breakers, REST refreshes, order tracking, wire link-id construction and `IntentExecutor.execute_place()` — so a blocked attempt mutates no placement-side state.
- `fresh` → proceed unchanged.
- `stale` / `no_data` → return before any state mutation or submission.
- Gate **only** `PlaceLimitIntent` submission. Do not gate `runner.on_ticker()` at orchestrator dispatch: the engine must still see events and emit intents so shadow mode stays observable, and `CancelIntent` must keep executing — cancelling on a stale price is safe and often desirable.
- In `retry_dispatch_place()`, return a failed `OrderResult` with a distinct error string per state, so a startup `no_data` is never reported as staleness in logs.

**Do NOT modify `retry_queue.py`.** An earlier draft wanted these results to be *terminal* (dropped, not backed off). That is not expressible without a fourth production file: `OrderResult` has no terminal flag (`apps/gridbot/src/gridbot/executor.py:142-149`), and `RetryQueue.process_due()` drops only successes plus four hard-coded error sentinels — `safety_cap*`, `truncate_breaker_blocked`, `duplicate_order_blocked`, `same_order_blocked` (`retry_queue.py:248-279`). Adding a fifth sentinel is possible but unnecessary, and the original rationale ("re-queuing against the same frozen price accomplishes nothing") was wrong: the price un-freezes when the feed recovers.

Let a blocked retry take the ordinary failure path instead. It backs off and is removed by whichever exhaustion rule hits first: `max_elapsed_seconds=30.0` with a "max time" WARNING (`retry_queue.py:205-212`), which in practice fires before `max_attempts=3` (`:196-201`); both queues are constructed with those values at `orchestrator.py:921-922`.

**Implementer trap:** the error strings chosen for these blocked results MUST NOT start with `safety_cap` and MUST NOT equal `truncate_breaker_blocked`, `duplicate_order_blocked` or `same_order_blocked` (`retry_queue.py:248-252`). Picking something like `safety_cap_ticker_stale` would silently take the drop path this plan deliberately rejected. Either way the grid level is not lost — the tracked order is left `failed`, `get_limit_orders` excludes it (`runner.py:725`), and the engine re-emits that level on the next fresh ticker. This keeps the change at 3 files and is strictly more conservative than dropping.

## Shadow mode

A blocked placement in shadow mode must log an intent-specific line containing `[SHADOW]`, the freshness state, symbol, side, qty, price, measured age and the configured maximum — and must not take the shadow executor's normal "Would place" path. This is an acceptance criterion: the skipped placement stays visible.

**Shadow mode does NOT suppress the alert.** The latch and `Notifier.alert()` behave identically in shadow and live. The VPS rollout runs staged with `shadow_mode: true`, so suppressing alerts there would hide the guard during exactly the phase meant to validate it. `test_shadow_mode_logs_blocked_placement` must assert the alert still fires, otherwise a shadow-suppresses-alert mutation survives.

## Alerting

Follow the edge-trigger convention established by feature 0105 (`docs/features/0105_PLAN.md`), including its rationale: a level-triggered alert here would fire every tick for the whole outage, which is the pathology feature 0026 removed.

- `Notifier.alert()` with a stable key `ticker_freshness_{strat_id}`.
- Per-runner unhealthy latch. Add it **only after** `alert()` returns; if it raises, log with `exc_info=True`, leave the latch clear for a later retry, and still block the order.
- **Re-arm on ANY `fresh` assessment, from either caller.** The latch is cleared by the shared assessment helper itself whenever it returns `fresh` — so both a fresh placement attempt AND the periodic sweep re-arm it. Two reasons this must not be periodic-only:
  - *Correctness:* clearing only on placement would leave the latch stuck whenever a fresh recovery produces no intents, silencing the next genuine outage. The periodic sweep covers that.
  - *Phase independence:* the Phase 2 edge test (stale, stale, fresh, stale ⇒ 2 alerts) drives the runner directly and must go green **inside Phase 2**, before the Phase 3 sweep hook exists. Putting the re-arm in the helper — not in the caller — is what makes each phase independently green.
- **Where the periodic assessment lives.** Put it in the per-runner loop of `_health_check_once()` (`orchestrator.py:1272`), NOT inside `_write_health_snapshot()`. The latter is wrapped in a deliberate swallow-all `try` whose failure is logged-and-ignored so a status-write error can never perturb the trading loop (`orchestrator.py:1378`, `:1442-1446`). A latch mutation placed inside it would be silently skipped whenever the snapshot write failed. `_health_check_once` computes the freshness; `_write_health_snapshot` only reports it.
- `no_data` blocks placement and logs one state line but sends no alert — a bot that has not yet received its first tick is starting up, not degraded.
- No per-intent heartbeat, no recovery alert. Repeated intents and repeated ticks inside one stale episode stay silent after the first message.

**Accepted, not fixed (same as 0105):** `Notifier.alert()` throttles per `error_key` for 60s (`notifier.py:18`, `:76-79`), so a second genuine stale edge arriving within 60s of the first is log-only — the ERROR line is written, Telegram is not. The edge-trigger test counts mocked `alert()` calls and will not surface this. Given a 15s threshold, two distinct edges inside one minute means the feed is flapping, and one message per minute is the desired volume anyway.

**Known limitation, stated not fixed:** the alert fires on a blocked *placement*, so a symbol that goes silent while no placement is pending produces no Telegram message. It still shows as `stale` in the health snapshot, which is the reporting path the issue asks for. A per-symbol silence alarm independent of placement activity is out of scope.

## Health reporting

Extend each per-strategy record in `_write_health_snapshot()` (`orchestrator.py:1371-1441`) with:

- `ticker_status` — `fresh` / `stale` / `no_data`
- `ticker_age_seconds` — non-negative rounded age, or `null` when there is no data
- `max_ticker_age_seconds` — that strategy's configured threshold

`stale` contributes to the existing `degraded` condition; a worse existing state still wins, and the forced initial `starting` state is unchanged.

**Before the first sweep** there is no assessment yet: `_write_health_snapshot(overall=HealthState.STARTING)` runs at `orchestrator.py:424`, ahead of any `_health_check_once`. The snapshot must report `ticker_status: no_data` / `ticker_age_seconds: null` in that window rather than raising on a missing strat key — a raise there is swallowed at `:1442-1446` and the whole `starting` snapshot would silently vanish. **`no_data` must NOT degrade**: the health sweep runs on a 10s cadence from startup, so degrading on "no tick yet" would flip the snapshot to degraded on the first sweep of every boot, before the first tick or during a slow startup reconcile.

This same per-sweep assessment is what re-arms the alert latch (see above).
