# Feature 0103 — Fail closed on truncated `get_open_orders` pagination

`BybitRestClient.get_open_orders()` currently returns a partial order set after reaching `max_pages`, allowing reconnect reconciliation to treat unseen live orders as cancelled. Add the existing opt-in truncation contract used by `get_executions_all()`, make reconnect reconciliation fail closed on incomplete data — skip only the absence-based mark-cancelled pass while still adopting the positive-evidence orders present in the fetched pages — and expose the event through health metrics, logs, and a throttled Telegram alert.

## Algorithm

1. `get_open_orders()` continues fetching and filtering pages exactly as today.
2. **Normalize the per-page cursor first** — `cursor = result.get("nextPageCursor") or None` — so Bybit's empty-string (`""`) end-of-list sentinel becomes `None`, mirroring `get_executions()` (rest_client.py:209). Only then compute `truncated = page >= max_pages and cursor is not None`, matching `get_executions_all()` (rest_client.py:256). Without the normalize, a complete response whose final page returns `nextPageCursor=""` at the `max_pages` boundary would false-positive as truncated — causing every such sweep to skip the mark-cancelled pass and fire a spurious truncation alert.
3. The empty-page break (`if not orders: break`) keeps the same *semantics* as `get_executions_all()` — Bybit signals end-of-list with an empty `list`, so an empty page terminates the fetch as complete (`truncated=False`). Note the loop *shapes* differ (`get_open_orders` breaks on empty before `page += 1` / cursor assignment at rest_client.py:681-689, whereas the sibling breaks after them); do not blindly transplant the sibling loop — compute `truncated` against this loop's actual `page`/`cursor` state.
4. Preserve the existing max-pages warning and final debug log regardless of `return_truncated`. Return only `orders` by default; return `(orders, truncated)` when explicitly requested.
5. `reconcile_reconnect()` calls `get_open_orders(..., return_truncated=True)`, records `orders_fetched` and `ReconciliationResult.truncated`.
6. **On truncation, skip ONLY the absence-based cancellation pass** — do NOT compute `missing_on_exchange` and do NOT call `mark_order_cancelled_by_order_id()`. An order tracked locally but absent from the *partial* fetch may still be live on an unfetched page; cancelling it locally is the exact false-cancel bug this feature closes. **Still run the positive-evidence injection pass**: compute `missing_in_memory` from the fetched partial set and `inject_open_orders()` those orphans. Orders present in the fetched pages were directly observed on the exchange — adopting them cannot be wrong, and it prevents the engine from placing a duplicate at that grid level on the next ticker. `truncated` is recorded per step 5 (immediately after the fetch/unpack, so an inject exception cannot lose it); this branch then populates `orders_injected` / `untracked_orders_on_exchange` from the injected subset and returns. (This matches the issue's literal acceptance criterion: "skip mark-cancelled pass," not "skip the whole compare.")
7. For a complete (non-truncated) response, retain the existing set-difference algorithm and cancellation/injection behavior unchanged.
8. Both orchestrator callers—`_order_sync_once()` and `_force_reconcile_strat()`—route the returned result through one truncation-reporting helper. Note `_force_reconcile_strat()` currently **discards** the `reconcile_reconnect()` return value (orchestrator.py:1649); capture it so the helper can inspect `truncated`. A truncated result:
   - increments `HealthMetrics.reconcile_truncations[strat_id]`;
   - calls `Notifier.alert()` with the fetched count and `error_key="reconcile_truncated_<strat_id>"`;
   - remains non-fatal so later periodic/forced reconciliations can recover.
9. In `_order_sync_once()`, **check `result.truncated` before the existing `if result.errors / elif injected / else "in sync"` ladder** (orchestrator.py:1857-1877). The `else` branch logs `"Order sync - in sync, %d orders checked"`, which the `gridbot-health` analyzer's `_ORDER_SYNC_RE` parses as the authoritative live book — a truncated partial count must never reach that branch.
10. The named counter appears under `metrics.reconcile_truncations` in the next `/tmp/gridbot_status.json` health snapshot (written by `_write_health_snapshot` from `_health_check_once`, NOT by `_order_sync_once`). `Notifier.alert()` also emits the reason at ERROR level, so the log-based `gridbot-health` analyzer sees it through its current error handling; no analyzer change is needed.
11. Forced reconciliation must continue its independent per-direction position-refresh pass (orchestrator.py:1664-1671) after reporting order-pagination truncation. Surfacing the pre-existing dropped-`result.errors` gap on the forced path is out of scope for this issue (see Constraints).

## Constraints

- Do not change `reconcile_startup()` or add a refuse-to-start check; commit `138737a` deliberately removed that behavior.
- Startup reconciliation stays on the default list-only path (no truncation flag). Adding startup-truncation observability is a separate concern, out of scope for #207.
- The pre-existing gap where `_force_reconcile_strat()` drops `reconcile_reconnect().errors` (only raised exceptions are alerted, orchestrator.py:1647-1654) is NOT addressed here — this feature captures the return value only to inspect `truncated`. General forced-path error alerting is out of scope for #207.
- Keep recorder `_snapshot_open_orders()` on the default list-only path.
- Do not add pagination configuration, status configuration, YAML, or database fields.
- Use snake_case, absolute imports, 88-character formatting, and existing logging/notifier conventions.
- No monetary arithmetic is introduced; any incidental monetary values remain `Decimal`, never `float`.
