# 0109 — Status-file consumer contract + cron watchdog (issue #258, Phase 1 ONLY)

## Context

Feature 0082 (`HealthStatusWriter`, `apps/gridbot/src/gridbot/health.py`) writes a
JSON snapshot to `status_file_path` (default `/tmp/gridbot_status.json`,
`apps/gridbot/src/gridbot/config.py:472`) once as `state="starting"` at the end of
`Orchestrator.start()` (`orchestrator.py:424`) and then every ~10s from
`Orchestrator._health_check_once` → `_write_health_snapshot` (`orchestrator.py:1380`,
`_HEALTH_CHECK_INTERVAL = 10`). **Nothing reads it.** `generated_at`
(`datetime.now(UTC).isoformat()`, tz-aware) is in every snapshot but no one checks its
age, so a crashed / SIGKILLed / OOM-killed / wedged process leaves a frozen file that
nobody notices.

Phase 1 of #258 = (1) define and document the consumer contract — **reject absent,
unparseable, or older-than-threshold snapshots; treat staleness as unhealthy; also treat
a non-healthy overall state as unhealthy** — and (2) build the actual watchdog. The user
chose a **cron watchdog** on the VPS (DigitalOcean droplet, ssh alias `gridbot-vps`, user
`gridbot`).

**Out of scope (Phase 2, do NOT plan):** writing `starting` before startup reconcile, a
terminal `failed` snapshot, `reasons[]`, last-success timestamps, threshold degradation,
in-bot transition alerts. **No change to `apps/gridbot` trading / orchestrator / health
producer code.** No automated deploy or run against live state — VPS install is an
operator runbook step gated on explicit user approval.

### Existing alert mechanism (research findings — reuse, don't rebuild)

- `gridbot.notifier.Notifier` (Telegram, throttled) lives **inside the bot process** and
  sends from a **daemon background thread** — unusable from a short-lived cron process
  (the thread is killed at interpreter exit, message silently lost) and dies with the bot
  (vps_plan.md Phase 4 explicitly requires an external alarm). So the consumer does NOT
  import `Notifier`.
- The VPS already runs an **external cron watchdog** (Phase 4c, gitignored
  `docs/deploy/VPS_STATE.local.md`): `/home/gridbot/gridbot/watchdog.sh` (chmod 700,
  untracked on the droplet), `gridbot` user crontab `*/5` with `CRON_TZ=UTC`; alerts to
  the same Telegram bot/chat (`TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID` in
  `/home/gridbot/gridbot/.env`) on supervisor FATAL/BACKOFF or RUNNING+log-stale>10m,
  quiet on STOPPED, 30-min throttle, `watchdog.sh test` hook. Process manager is
  `supervisord` (`supervisorctl status gridbot`).
- **Decision:** the repo deliverable is a pure, hermetically-tested Python consumer +
  CLI that returns an exit code and a one-line verdict; the existing `watchdog.sh` calls
  it in its RUNNING branch and routes a non-zero verdict through its **existing**
  Telegram send + throttle. No new alert channel, no new cron line (the existing `*/5`
  entry covers it), no pyproject/console-script change (invoked as
  `python -m gridbot.status_check`, so no `uv.lock` churn).

## Consumer contract (normative — documented in `.claude/rules/gridbot.md`)

Given `path`, `now` (tz-aware UTC) and `max_age_seconds` (default
`_DEFAULT_MAX_AGE_SECONDS = 60` = 6 missed 10s sweeps; head-room for blocking REST calls
on the main loop), evaluate in order, first failure wins:

1. **missing** — file does not exist (`FileNotFoundError`).
2. **malformed** — any of: other `OSError` on read (permission, is-a-directory; detail
   says "unreadable"; the file is read as **bytes** and decoded explicitly with
   `.decode("utf-8")`, never locale-dependent text mode); body is not valid UTF-8 or not
   valid JSON (includes empty file;
   catch `(ValueError, RecursionError)` — `ValueError` covers `UnicodeDecodeError` and
   `JSONDecodeError`, `RecursionError` covers pathologically nested JSON); top-level is not a
   JSON object; `generated_at` absent / not a string / not parseable by
   `datetime.fromisoformat` / naive (no tzinfo); `state` absent / not a string / not a
   `HealthState` value; `generated_at` more than `max_age_seconds` in the future
   (a same-host clock cannot legitimately do that; an unchecked future stamp would mask a
   frozen file indefinitely).
3. **stale** — `now − generated_at > max_age_seconds` (strict `>`; age == threshold is
   fresh). Staleness is unhealthy **regardless of the recorded `state`** (a frozen
   `healthy` file is the primary failure mode).
4. **unhealthy** — fresh, but `state` ∈ {`degraded`, `auth_cooldown`, `circuit_open`}.
5. **ok** — fresh and `state` ∈ {`healthy`, `starting`}. `starting` is accepted because it
   is written once and is superseded by the first sweep ~10s later; a wedged startup
   stops refreshing it and is caught by rule 3.

Reader never sees a torn file: the producer writes tmp+fsync+`os.replace` (atomic
rename), so rule 2 fires only on genuinely bad content. Only `state` and `generated_at`
are part of the contract; all other keys are ignored (forward-compatible with Phase 2's
`reasons[]` / last-success fields).

## Files

### New: `apps/gridbot/src/gridbot/status_check.py`

Stdlib + `gridbot.health.HealthState` only (`gridbot/__init__.py` and `health.py` are
stdlib-only, so a cron invocation stays light on the 1 GB droplet — no pybit / DB /
config import).

- `class StatusReason(StrEnum)`: `OK`, `MISSING`, `MALFORMED`, `STALE`, `UNHEALTHY`
  (values lower-case strings, same style as `HealthState`).
- `@dataclass(frozen=True) class StatusVerdict`: `reason: StatusReason`,
  `state: Optional[str]`, `age_seconds: Optional[float]`, `detail: str`; property
  `healthy` → `reason is StatusReason.OK`; method `format_line(path)` → one line:
  `OK state=<s> age=<a>s path=<p>` or
  `ALERT reason=<r> state=<s|-> age=<a|->s path=<p> detail=<d>`.
- Module constants: `_DEFAULT_STATUS_PATH = "/tmp/gridbot_status.json"` (mirrors the
  config default), `_DEFAULT_MAX_AGE_SECONDS = 60`, `_OK_STATES` =
  {`HealthState.HEALTHY`, `HealthState.STARTING`}.
- `check_status(path: str, *, now: datetime, max_age_seconds: float) -> StatusVerdict`
  — pure evaluator implementing the contract above; `now` injected for hermetic tests;
  raises `ValueError` if `now` is naive or `max_age_seconds` is not finite and `> 0`
  (`not (math.isfinite(v) and v > 0)` — rejects `nan`/`inf`, which would otherwise make
  every file "fresh"). Never raises for bad
  file content (that is a verdict, not an exception).
- `main(argv: Optional[list[str]] = None) -> int` — argparse: `--path` (default
  `_DEFAULT_STATUS_PATH`), `--max-age-seconds` (float, default 60; argparse `type`
  helper rejects non-finite or `<= 0`, incl. `nan`/`inf` → exit 2). Calls `check_status(..., now=datetime.now(UTC))`,
  prints `verdict.format_line(path)` to stdout, returns `0` if healthy else `1`.
- `if __name__ == "__main__": sys.exit(main())` (entry used by cron:
  `python -m gridbot.status_check`).
- Google-style docstrings on public items; module docstring states the contract and
  references #258 / 0082. No logging config (CLI output is the single stdout line).

### New: `docs/deploy/status_watchdog.md` — operator runbook (tracked, no secrets)

Every VPS step is **👤-gated: executed only after explicit user approval**, one step at a
time (live mainnet bot). Content:

1. Read-only pre-checks: `grep -n status_file ~/gridbot-etc/gridbot.yaml` (confirm the
   effective path; default `/tmp/gridbot_status.json`) and
   `grep -n status_file_enabled ~/gridbot-etc/gridbot.yaml` (abort if `false`),
   `jq '.state,.generated_at'` on that file (abort unless `generated_at` is within the
   last 60s — a fresh file proves the path is the one the bot actually writes, including
   any `${VAR}` expansion), `cat ~/gridbot/watchdog.sh` to locate its existing RUNNING branch, Telegram
   send function and throttle mechanism. Uptime-source pre-check (while supervisor
   reports RUNNING): `supervisorctl pid gridbot` must print a numeric PID (not `0`) and
   `ps -o etimes= -p "$(supervisorctl pid gridbot)"` must print an integer — abort the
   rollout if either fails.
2. Code update: `cd ~/gridbot && git pull && ~/.local/bin/uv sync --locked`. **No bot
   restart** (the running process never imports the new module; the watchdog is a
   separate process). Warn: the pull also stages any other merged changes for the next
   restart — confirm `git log` delta with the user first.
3. Manual dry run: `~/gridbot/.venv/bin/python -m gridbot.status_check --path <path>
   --max-age-seconds 60; echo $?` → expect `OK state=healthy …`, exit 0. Negative probe
   against a non-existent path → `ALERT reason=missing`, exit 1.
4. `watchdog.sh` extension (backup first: `cp watchdog.sh watchdog.sh.bak`): inside the
   existing **supervisor RUNNING** branch only (STOPPED stays quiet — an intentionally
   stopped bot leaves a stale file by design), and only when the bot process uptime ≥
   `STATUS_GRACE_SECONDS=360`. Uptime is taken as integer elapsed seconds via
   `up="${STATUS_UPTIME:-$(ps -o etimes= -p "$(supervisorctl pid gridbot)" 2>/dev/null | tr -d ' ' || true)}"`
   (`|| true` keeps a failed `ps` from aborting a `set -euo pipefail` script;
   `STATUS_UPTIME` is a manual-test override only, used in step 5) — **never** by
   parsing the free-text `uptime H:MM:SS` / `uptime N days, H:MM:SS` from
   `supervisorctl status` (breaks after 24h of uptime). If `up` is empty or non-numeric,
   treat it as "past grace" and run the check (fail toward alerting, not silence); the
   comparison is `[ "${up:-999999}" -ge 360 ]` after a `case` numeric guard. 360s is sized from the
   worst-case startup before the first `starting` write (`orchestrator.py:424`): each
   fail-closed fetch phase is 4 attempts × 10s REST timeout + `(2, 5, 10)` backoff
   sleeps ≈ 57s (`_INSTRUMENT_FETCH_BACKOFFS`, `_STARTUP_RECONCILE_BACKOFFS`,
   `orchestrator.py:60-61`), × 2 strats for instrument fetch + 2 for startup reconcile
   ≈ 230s, plus imports and the position fetch (≤ 60s) — ≈ 290s of REST retry budget.
   This is not a hard upper bound: `_connect_websockets` (`orchestrator.py:391-393`,
   pybit `retries=0` = reconnect forever) and multi-page `get_open_orders` can extend it.
   A startup that has not reached its `starting` write within 360s alerts **by design**:
   a bot still stuck in `start()` after 6 min is not managing positions. The grace also covers the
   previous process's leftover file after a restart, and the empty `/tmp` after a reboot.
   - **Restart-loop guard (grace must not hide a crash loop).** supervisord marks the
     bot RUNNING after `startsecs=30` (`vps_plan.md:86-88`); a process that dies between
     30s and 360s is auto-restarted forever without reaching FATAL, the log stays fresh,
     and every cron sample lands inside grace. So the grace branch is not a silent skip:
     it increments a counter file (`$STATE_DIR/status_grace_count`, where `STATE_DIR` is
     set explicitly at the top of the snippet to the directory the existing throttle
     files live in, found in step 1 — never left undefined under `set -u`; a missing
     counter file reads as 0, and so does empty or non-numeric content — same `case` numeric
     guard as `up`, so a corrupt counter can never abort a `set -euo pipefail` script). The past-grace RUNNING branch resets it to 0, and so does
     every other non-RUNNING, non-STARTING state (STOPPED, BACKOFF, FATAL, EXITED — an
     intentional stop/start or a FATAL already alerted by the existing branch must not
     leave old counts behind); STARTING samples leave it untouched, so a loop sampled
     partly in STARTING is still counted. A single ordinary restart contributes at most
     two in-grace samples (360s grace / 300s cron period) before a past-grace sample
     resets it, so the threshold of 3 never fires on one restart. When the counter reaches `STATUS_GRACE_MAX_RUNS=3`
     (three consecutive in-grace RUNNING samples = detection ~10–15 min after loop
     onset at `*/5`), send
     `ALERT reason=restart_loop uptime=<up>s` under its own `restart_loop` throttle key
     (separate from `status`, so a restart-loop page never suppresses a later
     stale/unhealthy page, and vice versa).
   - Past grace, run the CLI capturing **both streams and the exit code**:
     `if out=$(STATUS_CMD 2>&1); then rc=0; else rc=$?; fi` — a bare
     `out=$(…); rc=$?` would abort a `set -e` script on exit 1 before alerting. On
     `rc ≠ 0` send
     `status_check rc=<rc>: <last 3 lines of out>` (never an empty message — a
     traceback, import error or argparse error on stderr is itself an alert, and
     `rc=1` with the normal `ALERT …` line reads naturally) via the existing Telegram
     function under its **own throttle key/file** (`status`) with the same 30-min window,
     so a liveness alert does not suppress a status alert and vice versa.
   - The status-file path is read from `STATUS_FILE="${STATUS_FILE:-<path from step 1>}"`
     at the top of the script, so step 5 can point the whole branch at a probe file.
   Exact shell snippet given in the runbook, to be adapted to the function names found in
   step 1.
5. Verify: `watchdog.sh test` still fires; then exercise the **complete new branch**
   (uptime gate → CLI → rc capture → `status` throttle → Telegram) without touching the
   bot: `cp <path> /tmp/status_probe.json`, wait > 60s, remove the `status` throttle file,
   run `STATUS_UPTIME=999 STATUS_FILE=/tmp/status_probe.json ~/gridbot/watchdog.sh` once
   by hand (the uptime override makes the probe independent of the live PID's age) →
   expect exactly one Telegram `status_check rc=1: ALERT reason=stale …`; run it again
   immediately → no second message (throttle works). Restart-loop branch: remove the
   `status` throttle file, run `STATUS_UPTIME=60 ~/gridbot/watchdog.sh` three times →
   exactly one `ALERT reason=restart_loop` on the third run (first `echo 0 >` the counter
   file and run all three back-to-back right after a `*/5` tick, so a cron run cannot
   reset the counter in between); then run once with
   `STATUS_UPTIME=999` (real file) → counter back to 0. Malformed-uptime fallback:
   `STATUS_UPTIME=abc` with the stale probe → treated as past grace, alert fires (remove
   the throttle file first). Never stop/kill the live bot to
   test. Then confirm quiet on the real file for ≥ 2 cron cycles and
   `status_grace_count` = 0.
6. Record in gitignored `docs/deploy/VPS_STATE.local.md` (Phase status line) that the
   watchdog now enforces the 0109 status contract.

Note in the runbook: `/tmp` is wiped on reboot (vps_plan.md §"Durable bot status path");
the grace window makes that benign, so moving `status_file_path` is optional and out of
scope.

## What could break / risks

- **False alerts on restart/reboot** — mitigated by the watchdog's 360s RUNNING-uptime
  grace (shell side, runbook), not by weakening the contract.
- **`degraded` noise** — dirty-REST is a per-sweep delta (blip), but C4 `rate_limited`
  and `ticker_status == "stale"` persist on every sweep while they hold
  (`orchestrator.py:1404-1411`), so a sustained episode WILL alert (intended — that is a
  real degraded condition); the 30-min throttle bounds repeats. If it proves noisy in practice, tuning is a follow-up (Phase
  2's threshold degradation addresses it at the source) — no knob added now.
- **Accepted gap — slow crash loop.** A bot that crashes and is auto-restarted more
  than 360s after each start is past grace on every sample, so the grace counter resets
  and no `restart_loop` fires. Accepted: between crashes it is managing positions and
  passes startup reconcile each time, and the watchdog's purpose (`vps_plan.md:102`) is
  unmanaged-position detection. PID-churn alerting is a possible follow-up, not Phase 1.
- **Accepted gap — non-RUNNING counter reset is not exercised in step 5** (it would
  require stopping the live bot); it is covered by reading the snippet in review.
- **Stale-healthy after failed startup** (#258 problem 2) remains a Phase 2 producer fix;
  the freshness rule already bounds exposure to the threshold window.
- Cron environment: invoke the venv interpreter by absolute path (no `uv run` in cron —
  no PATH/lock resolution, lighter on 1 GB RAM).
