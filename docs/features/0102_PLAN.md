# Feature 0102 — Account-Wide Liquidation Halt for Shared-Wallet Replay

## Context

GitHub issue #246 resolves feature 0094 Open Question O1. The shared-wallet replay already couples strategy equity and aggregates account IM/MM, but each runner’s liquidation estimate subtracts only its own symbol’s MM. A combined account can therefore replay past the point where `total_equity - Σ total_mm <= 0`.

The merged loop currently performs `last_prices[symbol] = tick.last_price` → collateral marks → funding → `process_fills` → account-wide `update_equity`/sample → `execute_tick` (`multi_engine.py:330-361`, funding at `:339-348`). **Two coupled ordering constraints (review findings, unanimous across all three reviewers):**

1. **Freeze must precede `process_fills`.** `event_follower` is the production `MultiReplayEngine` path (`apps/live_check/src/live_check/runner.py`), and in that mode a fill's *reactive* open placement is dispatched **inside** `process_fills` via `self._engine.on_event(synthetic_ticker, ...)` + `self._dispatch_intents(...)` (`apps/backtest/src/backtest/runner.py:522-539`); `execute_tick` merely client-id-dedups those already-placed orders. A gate placed only *after* `update_equity` cannot freeze the breach tick's own opens.

2. **Equity must be marked-to-market at this tick's price before the pool is evaluated.** `session.total_equity` is **not** repriced when `last_prices` is refreshed (`:330`) or when `update_collateral_mark` runs — the latter only *stores* the mark and folds it in at the next `refresh_balances`/`update_equity` (`session.py:289-295`). So at the top of the tick, `total_mm` reflects this tick's `last_price` but `session.total_equity` still carries the *prior* tick's equity. A breach driven by **this tick's unrealized loss — the crash case AC1 exists for — would be invisible** if the pool used stale equity. The coordinator already intercepts `session.refresh_balances` to mark equity to Σ-unrealized at cached last prices (`multi_engine.py:181-195`); the halt must call it before evaluating the pool.

Therefore the halt observes account risk at **two sample points per tick, both on fresh-price (MTM'd) equity**, through one idempotent shared observer: (1) a **pre-fill** point — after `last_prices` refresh, collateral marks, and funding, call `session.refresh_balances(Decimal("0"))` (the coordinator override discards the argument and MTMs Σ-unrealized at cached last prices) to MTM equity at this tick's prices, then evaluate `pool = total_equity - total_mm`, track `min_account_pool`, and latch — all **before** `process_fills`, so a *unrealized-loss* breach freezes this tick's own reactive opens; and (2) a **post-fill** point — after the existing `update_equity`/`_account_sample`, re-observe (reusing the sample's `total_mm`) so a *fill-driven* breach (resting opens filling raise MM) is caught and the post-fill trough enters `min_account_pool`. Because `halt_new_opens()` is engine state checked inside `on_event`, once latched every subsequent `process_fills`/`execute_tick` call on every engine is gated. The replay continues processing fills, cancellations, reduce-only de-risking, and account samples.

## Account-Pool and Halt Algorithm

1. Initialize coordinator state once per run:

   - `account_halted = False`.
   - `liq_ts = None`.
   - `min_account_pool = Decimal("Infinity")`, the minimum identity and explicit sentinel for a run with no marked combined position.

2. Add `_SharedSessionCoordinator.total_position_value()` using every runner’s cached own-symbol price and the sum of its long and short sizes. Use gross position value, not net exposure, so hedged books still count as real positions. Mirror `total_im_mm()`'s `price <= 0` skip: a seeded position on a symbol with no at-or-before-start mark is invisible to the MM sum and this flat-guard until its first own tick — this is the pre-existing 0094 O2 idle-book behavior and now also affects `min_account_pool` / breach timing; note it, do not fix it here.

**Shared observer helper.** Define one idempotent coordinator method — `observe_account_risk(exchange_ts, total_equity, total_mm, combined_pv)` — used at **both** sample points below:

   - If `combined_pv > Decimal("0")`, lower `min_account_pool` with `pool = total_equity - total_mm`. Flat samples (`combined_pv == 0`) must not affect it.
   - **Latch iff `pool <= Decimal("0")` AND `combined_pv > Decimal("0")` AND `not account_halted`.** The `combined_pv > 0` gate prevents a flat account with zero/negative equity (e.g. fee-driven) from being falsely reported liquidated, mirroring `_p11`'s flat sentinel (`_p11_amount_sweep.py:173-181`). On latch: set `account_halted = True`; store `exchange_ts` as `liq_ts` (first breach only — never overwritten); call `halt_new_opens()` on every runner's public `engine` property, including engines whose symbols are idle on the breach tick; emit one warning (timestamp, equity, MM, pool). No per-tick logging.
   - **Idempotent:** once `account_halted`, the latch/warning/fan-out are a no-op; only `min_account_pool` keeps tracking. Because latch and minimum are folded in the **same** call, any call that latches also drives `min_account_pool <= 0`, so `liquidated == True` ⇒ `min_account_pool <= 0` holds regardless of which sample point fires.

   **Two sample points are required** (review finding, Codex+Cursor unanimous): a pre-fill point catches this tick's *unrealized-loss* breach and freezes the breach tick's own `event_follower` reactive opens (dispatched inside `process_fills`); a post-fill point catches a *fill-driven* breach (resting opens filling raise MM — the crash-endgame path) and captures the post-fill trough in `min_account_pool`. Both points feed the observer **fresh-price (MTM'd) equity**, so there is no stale/fresh basis split (the flaw of an earlier two-point revision); the invariant above holds at each.

3. **Pre-fill sample (before `process_fills`).** After `last_prices[symbol]` refresh, collateral marks, and funding (`multi_engine.py:339-348`) — ordering pinned **collateral → funding → MTM → observe → `process_fills`**:

   - **MTM equity first:** call `session.refresh_balances(Decimal("0"))` so `session.total_equity` reflects this tick's prices. The coordinator override **discards its argument** and recomputes Σ-unrealized at cached last prices (`multi_engine.py:181-195`), so pass the canonical `Decimal("0")` — do **not** pass `coordinator.total_unrealized()`, which would compute the Σ twice per tick for nothing. Without this, a breach driven by this tick's unrealized loss is invisible until after `process_fills`. `refresh_balances` rewrites `current_balance` and `total_equity` only (not the equity curve/drawdown/margin peaks — `session.py:333-335`). **Invariant to preserve (AC3 sizing parity):** nothing on the placement/sizing path reads `current_balance` between this top-of-tick refresh and the next `refresh_balances` inside `process_fills`/`_process_fill` (today `execute_place` sizing reads it only after the intra-fill refresh at `runner.py:642` and after the post-fill `update_equity`); a Phase-5 assertion or note must pin this so the added MTM call cannot silently perturb qty sizing.
   - Compute `total_im, total_mm = coordinator.total_im_mm()` and `combined_pv = coordinator.total_position_value()` from the cached `last_prices`, then call `observe_account_risk(...)`.

4. Run `process_fills` and `update_equity` as today, and append the existing `AccountCurveSample`. **Post-fill sample:** immediately reuse the `total_mm` already computed at `multi_engine.py:353-355` for the account sample (post-fill `total_equity` from `update_equity`, post-fill `combined_pv`) and call `observe_account_risk(...)` again. This adds no extra `total_im_mm` (it reuses the sample's) — only the pre-fill point in step 3 adds one `total_im_mm` per tick. The dual observer also adds a second `total_position_value()` call per tick (pre- and post-fill); it is a trivial size-sum. Both accepted for multi-million-tick sweeps.

5. Call the active runner's `execute_tick`. Both samples ran before it, so no new open is placed once latched. Residual (documented, matches `_p11` granularity): a fill-driven breach's own `event_follower` reactive open, dispatched mid-`process_fills` before the post-fill sample, is bounded to that one fill-batch — the freeze holds for `execute_tick` and every subsequent tick.

6. `GridEngine.on_event` must still perform normal grid-state processing, then filter its resulting intents:

   - Drop only `PlaceLimitIntent` values whose `reduce_only` is false.
   - Preserve reduce-only `PlaceLimitIntent`s.
   - Preserve `CancelIntent`s.
   - Make the halt one-way and idempotent; there is no resume operation.

   This covers both ordinary `BacktestRunner.execute_tick` placement and event-follower synthetic ticker placement without monkeypatching. Existing orders, fills, wind-down behavior, and account sampling continue unchanged.

7. Return the latched state directly on the frozen `MultiReplayResult`:

   - `liquidated: bool`
   - `liq_ts: Optional[datetime]`
   - `min_account_pool: Decimal`

   Direct fields are preferred over a new account-result struct because there is one account per `MultiReplayResult`. `Decimal("Infinity")` means no tick had a positive combined marked position value; every observed monetary value remains a `Decimal`. **Downstream note:** any sweep driver / CSV that prints `min_account_pool` must special-case `Decimal("Infinity")` (render as e.g. `n/a`) — call this out in the result-field docstring so drivers do not emit a bare `Infinity`.

## Halt Semantics — what the latch does and does NOT stop (review finding)

The halt is a **counterfactual** overlaid on a recorded run; be explicit about its boundary so the crash-drawdown analysis reads it correctly:

- **New OPEN placements** (non-reduce-only `PlaceLimitIntent`) are frozen account-wide in **both** fill modes once latched. This is the v1 guarantee (issue AC1), matching `_p11`'s scope.
- **Reduce-only placements and `CancelIntent`s remain allowed** so a frozen account can still de-risk.
- **`event_follower` mode (production):** the account was not actually halted live, so we do not rewrite the recorded tape. But be precise about what "replays" after `liq_ts`: recorded fills for orders that were *resting before* the latch still apply; recorded fills for opens the strategy would have placed *after* `liq_ts` have **no matching active replay order** and fall to `live_only` at the fixpoint (`apps/backtest/src/backtest/runner.py:540-553`), so they do not grow our modelled position. The post-`liq_ts` account curve and match-rate metrics are therefore **counterfactual, not live-faithful** — `liq_ts` is the survival cutoff for analysis and `min_account_pool` captures the closest-to-liquidation cushion.
- **Fill-sim mode:** matching is synthetic, so pre-latch resting opens *could* still fill and grow the book after the latch. v1 leaves resting synthetic opens in place (simplicity, matches `_p11`, which also does not cancel); `liq_ts`/`min_account_pool` mark the breach. Cancelling resting non-reduce-only orders at latch is an explicit **out-of-scope** follow-up (see Out of Scope) — noted here so the book-growth behavior is documented rather than surprising.

This subsection resolves the "book can grow after liquidation" review concern by making the boundary an explicit, tested decision rather than an unstated assumption.

## MM-Basis Decision

Use the coordinator’s existing 0045 `total_mm` unchanged for both the account curve and liquidation gate. This keeps every strategy in a multi-symbol experiment on one hedge-aware IM/MM basis and avoids recomputing an incompatible account MM beside the value already supplied to `session.update_equity`.

**Accuracy note (review finding):** `_estimate_pair_im_mm`'s price argument is *named* `mark_price` (0045's hedge formulas are mark-based), but the coordinator currently feeds it the cached **`last_price`** (`_last_prices`, seeded from `tick.last_price` and startup `TickerSnapshot.last_price`), not a separate mark feed. So the account `total_mm` — and hence this gate — inherits the existing 0094 behavior of using `last_price` as the mark proxy. This is intentional for #246: the gate reuses the *same* `total_mm` already driving `session.update_equity` and the account curve, so the liquidation check is consistent with the equity it is compared against. Introducing a distinct mark feed (true last-vs-mark divergence) would change existing 0094 account-curve behavior and is **out of scope** here; the `_p11` `P11_MARK_MM` note documents the mark-vs-entry sensitivity for the single-symbol baselines.

Do not add an entry/mark runtime toggle in #246. A toggle would permit otherwise identical shared runs to use different liquidation definitions and adds configuration solely for compatibility with a research harness.

For apples-to-apples single-symbol baselines, rerun each symbol through `MultiReplayEngine` with one strategy so it uses the same 0045 path. Existing `_p11` entry-based results must be labeled as a mark-versus-entry sensitivity, not treated as a direct baseline. `_p11`’s `P11_MARK_MM` option changes its notional price basis but still does not reproduce the full 0045 hedge-aware calculation.

## Acceptance Criteria

1. A shared-wallet run whose combined `pool = total_equity - total_mm` reaches `<= 0` latches an account-wide halt. A breach driven by unrealized loss latches at the pre-fill sample, before the breach tick's placement phase; a breach driven by a fill within `process_fills` latches at the post-fill sample that same tick (its own mid-fill reactive open is the documented one-fill-batch residual). Once latched, all strategies freeze new opens, reduce-only placements remain allowed, and the breach is exposed rather than silently replayed through.
2. `MultiReplayResult` exposes `liquidated: bool`, `liq_ts: Optional[datetime]`, and `min_account_pool: Decimal`.
3. When the combined pool never breaches, trading behavior and 0094 parity remain unchanged; all existing shared-wallet and multi-replay regression tests pass.
4. The halt uses the explicit 0045 account `total_mm` basis. Documentation records the mark-versus-entry sensitivity and the matching-0045 single-symbol baseline protocol.
5. Hermetic unit and integration coverage proves: breach freezes both books while preserving reduce-only placement, no breach preserves existing behavior, and `min_account_pool` is correct without flat-period pinning.

## Out of Scope

- Partial or tiered liquidation and Bybit ADL behavior. Version 1 is a binary, latched account halt using the same simplification as `_p11`; it does not synthesize exchange liquidation fills.
- Per-symbol liquidation-price fidelity under the shared pool beyond the combined account-pool gate.
- Cancelling pre-latch resting non-reduce-only orders at the halt (fill-sim book-growth after `liq_ts`) — documented under Halt Semantics; a follow-up if fill-sim post-halt book-growth proves material.
- A distinct mark-price feed for account MM (true last-vs-mark divergence) — the gate reuses the existing `last_price`-fed `total_mm`; see MM-Basis Decision.
- Suppressing recorded `event_follower` executions after `liq_ts` — recorded reality replays unchanged; `liq_ts` is the analysis survival cutoff.
