# 0110: Restore private executions and verify recording completeness

Implement issue #271, “[P1] Восстановить приватные исполнения и проверять полноту записи”, covering findings 4 and 5 of audit #270.

REST recovery must accept `result.category` with executions in `result.list[]`. Missing execution PnL must remain unknown. Persist private-stream coverage and recovery outcomes, then extend the existing freshness gate so incomplete recordings cannot produce PASS.

Two issue requirements govern the implementation:

> Отсутствующий PnL закрытия остаётся неизвестным до восстановления из достоверного источника; он не подменяется нулём.

> Свежий публичный тикер сам по себе не даёт PASS.

Phase A is one PR in two TDD cycles: (1) the consumer RED rows (the `test_sum_realized_*`, replay, backtest, comparator, render and `test_unknown_execution_pnl_skips_validation` rows) + GREEN steps 6 and 7, implemented FIRST and committed green; (2) only then the producer RED rows (ported audit test, adapter, gridcore, reconciler, normalizer, writer, repository) + GREEN steps 1–5; the RED table and GREEN list below are numbered for reference, not implementation order (the producer changes that start emitting NULL), so no intermediate commit feeds NULL into a zero-substituting consumer (`comparator/loader.py:165`, `replay/engine.py:~528`, `multi_engine.py:~749`). Split Phase B into two dependent PRs: recording persistence, then live-check integration. Every PR follows RED → GREEN → REFACTOR.

2. **Preserve missing PnL.** Parse REST rows' PnL with the same parser as WS (`normalizer.py:230`: present → `Decimal(str(x))`, missing/null/empty → `None`). The documented REST execution list has neither `closedPnl` nor `execPnl`, so recovered rows persist `closed_pnl=None`. 3. **Choose trustworthy enrichment only.** For this issue, leave REST-only PnL unknown. Accept documented WS `execPnl` for the same execution identity. Do not allocate `/v5/position/closed-pnl` values across executions: that endpoint aggregates by order, and allocation would require separate fee, partial-fill, and window-boundary reconciliation.

4. **Allow NULL through ingestion.** Make `ExecutionEvent.closed_pnl` optional with an unknown default. Normalize present numeric values with `Decimal(str(x))`; missing/null/empty PnL becomes `None`. Preserve explicit numeric zero. The writer already passes the field through and must continue doing so.

5. **Enrich via COALESCE upsert, no new operation.** The only real case is the race where a REST NULL row lands before the buffered WS row, which today loses to `ON CONFLICT DO NOTHING` (`shared/db/src/grid_db/repositories/execution.py:~131-135`). Change `bulk_insert`'s conflict clause to `DO UPDATE SET closed_pnl = excluded.closed_pnl WHERE private_executions.closed_pnl IS NULL AND excluded.closed_pnl IS NOT NULL`. The `WHERE` predicate is required: SQLite `rowcount`/`changes()` counts rows touched by `DO UPDATE`, so an unconditional update would count every duplicate as inserted (breaking `test_bulk_insert_skips_duplicates`, `shared/db/tests/test_repositories.py:782`). Return `affected` (inserted or enriched) and `unchanged` counts; update the callers that read the return value (`execution_writer.py:98`, `reconciler.py:318`) and the tests asserting an int (`shared/db/tests/test_repositories.py:779`, `:861`, `:867`; `tests/integration/test_eventsaver_db.py:197`, `:223`, `:243`). Recovery needs only these. Dedupe each batch by `exec_id` first, keeping the member with a known PnL (the Postgres branch raises "cannot affect row a second time" on in-batch duplicates, and the writer would requeue forever). `exec_id` is globally unique (0083 invariant) and REST never supplies a known PnL, so no identity cross-checks and no conflict error. Nothing may raise out of `ExecutionWriter._flush_internal` for a redelivery (it requeues the whole batch on any exception, `execution_writer.py:111-114`, and would retry forever).

6. **Stop unknown data before arithmetic.**

### GREEN: minimum implementation

**Schema change requiring user confirmation.** Two new tables in `shared/db` models; the recorder creates them via `create_tables()` on start (`apps/recorder/src/recorder/main.py:85`, `prepare_session.py:90`, `:213`), so no migration script is needed (earlier `migrate_*` scripts exist only for `ADD COLUMN`). The repository rule at `.claude/rules/code-style.md:40` — “Database migrations: always confirm before running; never drop tables without approval” — still applies: confirm before the new recorder runs against an existing DB.

- `private_stream_sessions`: autoincrement `id` PK, `run_id` (`ForeignKey("runs.run_id", ondelete="CASCADE")`, matching `models.py:281`), `account_id`, `connected_at`, `last_checkpoint_ts`.
- `private_stream_gaps`: autoincrement `id` PK, `run_id` (same CASCADE FK), `account_id`, `symbol`, `gap_start`, nullable `gap_end`, `recovery_status` (`pending`/`recovered`/`skipped`/`truncated`/`failed`), `inserted`, `duplicates`, nullable `reason`. Index `(run_id, account_id, symbol, gap_start)`.

New `shared/db/src/grid_db/repositories/private_stream.py`, synchronous (open session, advance checkpoint, open gap, close gap, set outcome). No buffered writer. Idempotency: `on_disconnect` inserts the open rows for all configured symbols in ONE transaction and stores their ids in memory only after commit; a duplicate `on_disconnect` is a no-op only for symbols that already hold an open id (a partial failure can't leave a symbol without a gap row). A symbol's open id is cleared only after its close-gap write commits, so the next outage opens a new row.

Lifecycle:

1. **Auth confirmation (collector-only).** Add blocking `PrivateWebSocketClient.wait_ready(timeout) -> bool`: pybit `self._ws.auth` is true (set at `_websocket_stream.py:479`) AND every subscription request sent in `connect()` (`ws_client.py:420-435`, stored in pybit `subscriptions[req_id]`) has a positive ack. pybit only logs acks (`_process_subscription_message`, `_websocket_stream.py:487-502`, called via `self.` at `:558`), so the client wraps that method on its own pybit instance to record `success is True` per `req_id` before delegating. The wrap is installed inside `connect()` right after constructing the pybit `WebSocket` and BEFORE the `*_stream()` subscribe calls, so it covers every new instance (`reset()` goes through `connect()`, `ws_client.py:513-524`) and no ack can arrive unobserved. Set `_PRIVATE_READY_TIMEOUT = 5 s` (named constant; must keep public connect + private ready + REST snapshot under the 15 s sentinel wait, see step 8). Only `PrivateCollector` calls it. `connect()` itself is unbounded today (pybit treats `retries=0` as reconnect-forever, `_websocket_stream.py:142-149`) and is called synchronously on the loop (`private_collector.py:~205-211`), so `PrivateCollector.start` runs `connect()` + `wait_ready()` together in one `_run_in_daemon_thread` call bounded by `_PRIVATE_READY_TIMEOUT` total — the same pattern as `reset()` (`private_collector.py:320-334`), never on the owner loop. Acks are keyed to the socket identity captured inside `connect()` when the wrap is installed; `wait_ready` returns False if that identity changes during the wait (a pybit silent reconnect resends the same `req_id`s, so stale acks from the old socket must not count). Ready timeout at start: `PrivateCollector.start` disconnects and raises; the recorder emits `RECORDER_SNAPSHOT_INCOMPLETE` and stops; standalone `EventSaver.start` (`event_saver/main.py:231`) catches it per account, logs ERROR and continues with the other accounts. Ready failure after a collector-initiated `reset()`: treated as unhealthy — the gap stays open, the identity baseline is not re-taken, no `on_healthy_probe`, and the next probe resets again. A rejected subscription already raises `KeyError` inside pybit (`topic[0]` of the stored JSON string) and exits the socket, which the dead-socket probe catches; the ack wait covers the delayed-ack window.
2. **Socket identity.** Expose the current pybit `WebSocketApp` object. The baseline is the identity captured inside `connect()` (so a silent reconnect during the ready wait is visible), re-taken only after a `reset()` whose ready wait succeeded; compare with `is` at each probe. pybit's silent reconnect (`restart_on_error=True` default, `_websocket_stream.py:38-39`, `:217-240`; our wrapper only passes `retries=0`, `ws_client.py:411-418`) shows up as an identity change. `restart_on_error` stays unchanged.
3. **Probe outcome.** Unhealthy = socket dead, identity changed, or not authenticated. On unhealthy: call owner `on_disconnect(start=gap_start)` BEFORE `reset()`, where `gap_start` = the collector's own last healthy probe time − `_LIVENESS_MARGIN` (tracked by `PrivateCollector` for every owner, so standalone EventSaver — which registers only `on_gap_detected`, `event_saver/main.py:104-113` — keeps a bounded gap start instead of today's `last_message_ts`); if it raises, skip `reset()` this probe (existing except path) so the gap row always exists before recovery work. After a confirmed reset: `on_gap_detected(start, end)`. Reset timeout/cancellation/shutdown leaves the gap open. On healthy: `on_healthy_probe(barrier_ts)`. The collector's last-healthy time starts at the ready-confirmation time, so a disconnect before the first probe still has a gap start. The recorder inserts the `private_stream_sessions` row right after confirmation with `connected_at = last_checkpoint_ts =` that time. `_LIVENESS_MARGIN = 75 s` (named constant). Derivation: pybit uses `ping_interval=20`, `ping_timeout=10` (`_websocket_stream.py:36-37`); websocket-client's `_send_ping` waits one full interval before entering its loop (`.venv/.../websocket/_app.py:239-251`), so the first ping goes out ~40 s after every open/reset, and the timeout is only checked after `select(ping_timeout)` returns (`_app.py:482-499`), i.e. 10–20 s after the ping. Worst-case half-open detection is therefore ≈ 2×20 + 2×10 = 60 s after connect/reset; +15 s scheduling slack. Until then the socket still reads `connected` (`ws_client.py:496-511`).
4. **Durable checkpoint barrier.** `on_healthy_probe` is an `async` callback that the health-check task awaits on the owner loop (today's owner callbacks are synchronous, `private_collector.py:366-441`; a blocking wait on futures that run on the same loop would deadlock). Under the lock of a recorder-owned thread-safe pending-future registry (the collector discards the callbacks' return values, `private_collector.py:~366-423`, so the recorder's private `_handle_*` callbacks register each `run_coroutine_threadsafe` future, `recorder.py:888-928`, inside that same lock), record `barrier_ts = now` and copy the registered futures; release the lock (so the pybit callback thread is never blocked during the flush), then await them (`asyncio.wrap_future`) (a single `sleep(0)` is not enough: the Task's first step is queued after the probe's resume); then retry any pending close-gap/outcome writes; then flush the execution, order, position and wallet writers. `flush()` returns `bool` (empty buffer → `True`; DB error → `False`, keeping the existing requeue). Publish `last_checkpoint_ts = barrier_ts − _LIVENESS_MARGIN` only if all of that succeeded (never moving it backward), so a probe during an undetected half-open period cannot certify it.
5. **Open-gap writes are direct.** The recorder's `on_disconnect` calls the repository directly (the probe already runs on the owner loop, `private_collector.py:274-290`) and lets DB errors propagate; one open row per configured symbol.
6. **Structured recovery result.** `reconcile_executions` returns `ExecutionRecoveryResult(status, inserted, duplicates, reason)` instead of `int` (query bounds go into the reason/log line only). Query window = `[gap_start − _RECOVERY_START_MARGIN, time recovery starts]` — no longer anchored to the account-wide last persisted execution (`repositories/execution.py:58-73`), which on a quiet account or across runs can exceed Bybit's 7-day `endTime − startTime` limit or pull prior-run rows; a window longer than 7 days → `failed` with that reason (margin 5 s, named constant: an execution with `execTime` just before the checkpoint may still have been in flight when the socket died; the end closes the auth→subscribe window). exec_id dedup makes both overlaps free. `recovered` only after a complete query and DB commit (zero inserted is fine). Any Trade-row conversion error → `failed`. Keep refusing to persist truncated backfills. `run_id=None` → `failed`. Gap below `gap_threshold_seconds` (`reconciler.py:229-231`) → `skipped`. `EventSaver._handle_private_gap` just logs the result.
7. **Persist outcomes.** `Recorder._handle_private_gap` (`recorder.py:955`) persists each symbol's result when its future completes (done-callback → repository), including failures. A failed close-gap or outcome write is kept in memory and retried by the next `on_healthy_probe` before any checkpoint advance.
8. **Startup order.** Move `_write_initial_rest_snapshot()` (`recorder.py:~150`) after `_init_collectors()` has a confirmed session, so the startup anchor (`exchange_ts=local_ts=snapshot_ts`) lies inside the session. The 0029 goal (a t=0 row for quiet accounts) is unchanged, and the replay seed pre-check is relative to `seed.at_ts`, not run start (`_SEED_PRE_CHECK_MARGIN = 5 s`, `apps/replay/src/replay/engine.py:~235-240`), so a snapshot landing seconds later does not affect it. Keep the feature 0055 sentinel contract (`scripts/phase4/start_recorder.sh:81-86` waits ≤ 15 s; `.claude/rules/recorder.md` requires every exit path to emit a sentinel): the private connect+ready timeout path emits `RECORDER_SNAPSHOT_INCOMPLETE` before raising, and `_PRIVATE_READY_TIMEOUT = 5 s` bounds connect + ready together. The public collector's `connect()` gets the same bounded treatment. The REST snapshot calls can already take up to 10 s each today (`rest_client.py:149-155`), so raise the launcher wait in `start_recorder.sh:81-86` from 15 s to 30 s and keep one end-to-end startup-deadline test. Update `apps/recorder/tests/test_initial_rest_snapshot.py` / `test_start_recorder_check.py` and the startup-order note in `.claude/rules/recorder.md`.
9. **Mark synthetic zero-rows.** In `_snapshot_positions` (`recorder.py:461-470`, `:537-575`) set `raw_json={"synthetic": <reason>}` on contract zero-rows (`rest_failure` / `malformed` / `absent_side`) instead of `None`, so live-check can tell a genuinely flat leg from a failed fetch. The 0034 NULL telemetry fields stay NULL.
10. **Flat hedge legs.** `PositionWriter` (`position_writer.py:~213`) stores `side=pos.get("side", "")`; Bybit sends `side=""` for an empty position, so a leg closing to flat never gets a `Buy`/`Sell` row. When `side` is empty, derive it from `positionIdx` (1 → `Buy`, 2 → `Sell`).

### Phase B1b implementation notes (as built)

B1b is detect-only: the collector now notices silent reconnects and unready sockets and dates the gap from the last healthy probe. Opening the gap row before reset stays in B1c.

- `PrivateWebSocketClient(track_subscription_acks=False)` is the default, so gridbot's pybit object is untouched. Only `PrivateCollector` turns it on. With tracking on, `connect()` wraps the instance's `_process_subscription_message` to record acked `req_id`s against the current pybit `ws.ws` (`WebSocketApp`). `wait_ready(timeout)` is true once `ws.auth` is set, the socket is still the one the acks came from, and every `ws.subscriptions` req_id is acked. Calling it without tracking raises `RuntimeError`. `socket_identity()` returns the current `ws.ws`, which pybit replaces on a silent reconnect under `restart_on_error=True`. `is_authenticated()` reads `ws.auth`.
- `PrivateCollector` is healthy when it was confirmed ready, the socket is alive and authenticated, and the identity still matches the baseline taken before `wait_ready`. A healthy probe stamps `_last_healthy_ts`. A gap starts at `_last_healthy_ts − _LIVENESS_MARGIN` (75 s: two pybit ping intervals and timeouts, plus 15 s slack), no longer at `last_message_ts`, so a quiet account no longer yields a multi-day window. The cost is that a short blip is reported as a gap of roughly 90 s. Dedupe makes the wider query harmless.
- Not ready at `start()` (5 s, `_PRIVATE_READY_TIMEOUT`): the collector logs ERROR and does not raise. The first probe re-checks the same socket before resetting (see below). Raising (`RECORDER_SNAPSHOT_INCOMPLETE`) waits for B1c's startup reorder.
- Not ready after a reset: the collector logs ERROR and reports no gap yet. `_last_healthy_ts` is kept, so the next probe reports the gap from the original start. The error line says how long the stream has been unready.
- Late readiness (PR #283 review): a probe that finds `_ready=False` first re-runs the readiness wait on the SAME socket if it is alive. Acks that landed after the 5 s timeout then make it ready: the socket is kept (a reset would restart the clock, so slow acks could loop forever) and the unready stretch is reported as a gap. Only a socket still not ready is reset. `wait_ready` raising (e.g. a pybit internals change) is logged once and counts as not ready, so `start()` never propagates it. A reset timeout still leaves no gap row; B1c opens the row before reset.
- `start()` still calls `connect()` on the event loop, as before B1b; only `wait_ready` runs in a daemon thread. Moving `connect()` off the loop with the readiness wait (the B1 design above) lands with the B1c startup reorder.
- A socket that never becomes ready (e.g. one topic rejected for a missing API-key permission while the others still deliver) is reset at most `_MAX_UNREADY_RESETS` (3) times in a row. After that it is kept on liveness-only health: `_ready` is set with the current socket as the baseline, one ERROR says so, and the gap is reported so REST backfill runs (PR #283 review round 2; resetting forever lost every stream and wrote no gap row). Any successful readiness clears the counter.
- A gap never starts before the collector's connect time (`_connected_at`), so a not-ready start does not query executions from before the run.
- Readiness matches acks strictly by `req_id` once any ack carries one; only if none ever does, it counts positive acks against the subscription count (so an unkeyed ack cannot stand in for an un-acked subscription). Bybit's docs show a private subscribe ack without `req_id` (in an example whose request sent none). gocryptotrader matches `/v5/private` subscribe and auth replies by `req_id` and notes only `/v5/trade` omits it, so the private stream echoes it; the count covers the case where it does not. After deploy, check that the recorder log has no "not ready" ERROR.
- Pulled in from the B1a review: `PrivateStreamGapRepository.set_outcome` takes `run_id` and only updates a row of that run. The reconciler logs a WARNING naming each dropped REST row (`execId`, or a truncated repr for non-dict rows).

### Phase B1c-1 implementation notes (as built)

B1c was split: B1c-1 (coverage: sessions, open gaps, checkpoint) and B1c-2 (startup reorder, bounded public/private connect, raise on not-ready at start, launcher 15→30 s). B1c-1:

- `private_stream_sessions` (`run_id` FK CASCADE, `account_id`, `connected_at`, `last_checkpoint_ts`; index `(run_id, account_id)`), created by `create_tables()`. `PrivateStreamSessionRepository` (in `repositories/execution.py`, next to the gap repository): `open_session` (checkpoint starts at `connected_at`), `advance_checkpoint` (run-scoped, never backward). `PrivateStreamGapRepository.close_gap` (run-scoped). The recorder opens the session right after `PrivateCollector.start()`; B1c-2 moves that behind a confirmed ready start.
- Collector hooks: `on_disconnect(gap_start)` is called after the gap start is computed and BEFORE `reset()`; if it raises, the outer `except` logs it and the reset is skipped this probe (the next probe retries with the same start). The recorder raises for at most 3 probes in a row (`_MAX_OPEN_GAP_FAILURES`); after that the reset goes ahead and the gap is recorded at reconnect, because a dead socket loses orders, positions and wallet snapshots that no REST call can recover (PR #286 review). `on_healthy_probe()` is awaited on each healthy probe unless the socket is kept on liveness checks only (`is_degraded()`); its errors are logged as "checkpoint failed" and do not make the socket unhealthy. The await is bounded (`_HEALTHY_PROBE_TIMEOUT`, 10 s) and ends at once on `stop()`; the recorder shields the writes it awaits, so a cancelled checkpoint cancels nothing (PR #286 review). The late-readiness path (no reset) does not call `on_disconnect`; the recorder records that gap closed at reconnect as in B1a.
- Recorder gap lifecycle: `_handle_private_disconnect` opens one row per symbol without an open row, in one transaction, and keeps the ids only after commit. `_handle_private_gap` closes each open row (`gap_end` = reconnect time) and forgets the id immediately, even when the close write fails, so the next outage always opens its own row. (The first version kept the id until the close committed; a queued close could then be replayed after a second outage had reused the row, moving `gap_end` backward — found in local review.) A symbol with no open row gets a closed row (B1a behaviour); if that insert fails it is queued too. A reset timeout leaves the rows open.
- Failed close / outcome / fallback-row writes are queued (`_pending_gap_writes`) and retried on every checkpoint attempt and every private gap; the checkpoint does not advance until the queue is empty. A `RowNotFoundError` is logged and dropped instead: retrying cannot fix it and would block the checkpoint forever. Any other `ValueError` is retried.
- Checkpoint barrier (`Recorder._private_checkpoint`): private WS writes go through `_submit_private`, which creates and registers the future under `_pending_lock`; the barrier takes `barrier_ts` and copies the futures under the same lock, awaits them, then flushes the execution, order, position and wallet writers (`flush()` now returns `bool`: empty → True, DB error → False with the batch requeued). Only then, and only if no gap row is open, `last_checkpoint_ts = barrier_ts − _LIVENESS_MARGIN` (never backward, so the first ~75 s after connect do not move it). `on_healthy_probe` takes no argument (the design above passed `barrier_ts`): the recorder must take the barrier time itself, under its own lock.
- A private write future that fails or is cancelled means an event never reached a writer. The write-lost latch (set under `_pending_lock`) blocks the checkpoint until `_record_lost_write_gap` has recorded a gap `[now − 75 s, now]` on the loop, then the checkpoint resumes. (The first version froze the checkpoint for the rest of the run; PR #286 review.)
- `Recorder.get_stats()` adds `private_ws: {"degraded": bool}` to the periodic `Health:` line.
- While a socket is kept on liveness checks only, healthy probes neither call `on_healthy_probe` nor stamp the collector's last-healthy time, so a later outage's gap starts at the moment it degraded (the degraded stretch is never certified). Each of those probes does one non-blocking readiness check; if the acks landed late on the same socket, liveness-only ends there, the degraded stretch is reported as a gap and checkpoints resume (external review round 2).
- `Recorder.start()` clears the coverage state, so `stop()` → `start()` (a new run) does not inherit a write-lost latch, open gap ids or queued gap writes.
- The write-lost latch is set inside `_pending_lock`, so the barrier sees either the failed future or the latch; configured symbols are de-duplicated in the gap open/close paths (external review round 1).
- Known limit (still open): events dropped before a writer's buffer (collector normalizer / callback errors, an order event with no `run_id`) are logged but not seen by the checkpoint; `flush()` returning True means "nothing left to retry", not "nothing was dropped".
