# Feature 0105 — Make TCP-dead WebSocket detections observable

## Context

`Orchestrator._ws_health_check_once()` currently detects dead TCP sockets and calls `reset()`, but emits neither an operator alert nor a reconnect metric (`apps/gridbot/src/gridbot/orchestrator.py:1443-1497`). The logical-connection path already records successful public and private reconnects (`apps/gridbot/src/gridbot/orchestrator.py:1298-1355`). This change gives the TCP-level path equivalent observability while preserving its private-only REST reconciliation behavior and preventing repeated dead probes from creating a *detection*-alert storm. The pre-existing reset-failure alert remains level-triggered — see "Accepted behavior".

## Edge-trigger algorithm

Add `_ws_dead_alerted: set[tuple[str, str]] = set()` in `Orchestrator.__init__`. Each entry is `(account_name, kind)`, where `kind` is exactly `"public"` or `"private"`. Production invokes `_ws_health_check_once()` from the main-loop `_tick()` path (`apps/gridbot/src/gridbot/orchestrator.py:652-664`), so this set requires no lock. `_on_ws_disconnect()` must never read or mutate it.

For each public and private client:

1. Build the channel key and call `is_socket_alive()` inside the existing per-client `try`.
2. If the probe returns `True`, remove the key with `discard()` and continue. This alive probe is the only re-arm operation; successful `reset()` must not clear the key by itself.
3. If the probe returns `False`, retain the existing WARNING.
4. For a private socket, call `_enqueue_post_recovery_reconcile(account_name)` on every dead detection, before alerting or resetting. This preserves the current detection-time behavior: reconciliation is scheduled even if notification or `reset()` later fails. The public branch must never enqueue.
5. If the key is not already present, emit the detection alert inside its **own** nested `try`/`except Exception`, and add the key to `_ws_dead_alerted` **only after** `alert()` returns:
   - Call `self._notifier.alert()` with message `Gridbot: WS socket dead for {account_name}/{kind}; resetting` and throttle key `ws_socket_dead_{kind}_{account_name}`.
   - On success, add the key.
   - If `alert()` raises, log ERROR with `exc_info=True`, do **not** add the key, and fall through to `reset()`. Rationale: `Notifier.alert()` starts a daemon thread (`apps/gridbot/src/gridbot/notifier.py:82-87`), which can raise under thread exhaustion. Letting that escape to the per-client handler would both skip the recovery `reset()` — violating the "every `False` probe attempts a reset" guarantee — and, if the key were latched first, permanently suppress the detection alert for that edge. Not latching on failure lets the next probe re-enter `alert()`, which always writes its `logger.error("ALERT: …")` line (`notifier.py:67`, before the throttle check) — so the event still reaches the log. It does **not** guarantee Telegram delivery: see "Accepted behavior".
6. Call `reset()` outside the edge-alert condition, so every `False` probe still attempts a reset while a persistent edge emits only one detection alert.
7. Immediately after `reset()` returns successfully, call `self._health_metrics.record_ws_reconnect(kind)`. Count every successful reset attempt, including repeated attempts during one persistent dead edge.
8. If `reset()` raises, retain the existing ERROR plus `alert_exception()` handling. Do not increment the metric, remove the edge key, or undo the private reconciliation enqueue. The latched key suppresses another detection alert until a later probe explicitly returns `True`.
9. If `is_socket_alive()` itself raises, execution goes directly to the existing exception handler before any edge mutation: do not add or remove the key, reset the client, record a metric, or enqueue private reconciliation. A previously latched key therefore remains latched. This is distinct from an exception raised internally by the real pybit probe, which the wrapper catches and reports as `False`, entering the normal dead-socket path.

## Accepted behavior

Consequences of this design that are understood and accepted, not defects to fix here. Document them in the `_ws_health_check_once()` docstring during Refactor; add no code for them.

- **Detection alerts surface at ERROR level.** `Notifier.alert()` unconditionally runs `logger.error(f"ALERT: {message}")` (`apps/gridbot/src/gridbot/notifier.py:67`), so each alive→dead edge now writes an ERROR line where today there is only a WARNING. That is the intended observability — but it means a dead socket will trip the `gridbot-health` analyzer's zero-ERROR-logs check, which today it does not. Intended, and the reason issue #259 (analyzer check 5) is tracked separately.
- **The reset-failure alert stays level-triggered.** The latch suppresses only the detection alert. When `reset()` keeps raising, the existing `alert_exception()` at `orchestrator.py:1469-1472` / `:1494-1497` fires on every 10s probe, bounded only by the notifier's 60s per-key throttle — up to ~1440 Telegram messages/day/channel during a sustained outage. Pre-existing behavior, explicitly not changed by this feature.
- **Spurious edge during an in-flight worker reset.** `reset()` clears `_ws` under the lock before `connect()` re-acquires it (`packages/bybit_adapter/src/bybit_adapter/ws_client.py:218-219`), and `is_socket_alive()` returns `False` when `_ws is None` (`:196-198`). A main-loop probe landing inside a concurrent `_on_ws_disconnect` reset therefore reads dead and emits one detection alert plus a second overlapping `reset()`. Public-only in practice: the private gap watchdog that drives `_on_ws_disconnect` is disabled (`orchestrator.py:872`). Edge-triggering caps this at one message per occurrence.
- **An `alert()` that raises can cost that edge its Telegram message, not just its latch.** `Notifier.alert()` stamps `_last_sent[key]` (`apps/gridbot/src/gridbot/notifier.py:79`) *before* `thread.start()` (`:87`), so a `start()` failure burns the 60s throttle window for that key. The next probe arrives 10s later, re-enters `alert()`, writes the `logger.error` line at `:67`, hits the throttle check at `:77-78`, returns normally — and the plan then latches. Net: the log records the edge twice, Telegram may record it zero times. Accepted rather than fixed: distinguishing "queued" from "throttled" would require changing `Notifier`'s return contract, which is out of scope, and the only known trigger (thread exhaustion) is already a process-wide failure in which the ERROR lines and the `ws_reconnects` counter remain the operative signals. The Refactor docstring must say "the retry is log-only inside the throttle window", not "retries the notification".
- **The reset-failure `alert_exception()` remains unguarded.** If the notifier raises there (`orchestrator.py:1469-1472` / `:1494-1497`), the exception escapes the per-client `except` and aborts the remaining clients for that tick, weakening the guarantee pinned by `test_isolation_one_failure_does_not_skip_others` (`apps/gridbot/tests/test_orchestrator.py:4054-4068`). Pre-existing on both the public and private branches and deliberately left alone — this feature guards only the detection alert it introduces. The next tick retries 10s later. Noted so the guarded/unguarded asymmetry reads as a decision, not an oversight.
- **No dead→alive recovery alert.** A successful `reset()` bumps `ws_reconnects` but never notifies, so a socket resetting every 10s for hours is indistinguishable in Telegram from a single blip. The operator gauges duration from the `ws_reconnects` counter in the health snapshot, not from alert volume. Adding a recovery alert is out of scope for #209.
