# Заголовок

live-check: PASS не подтверждает корректность бэктеста и полноту записи лайва

# Текст issue

`live-check` запускает seeded replay в режиме `event_follower` и сравнивает его с записанными данными лайва. В текущем состоянии положительный результат возможен при неправильном расчёте PnL, неправильных размерах ордеров и неполной записи биржевых событий. До исправления этих случаев PASS нельзя использовать как критерий доверия к обычному бэктесту.

Аудит выполнен на `8e60a8639ded44021afaff940fa43386930a670e` без доступа к торговому счёту. Детали, строки кода и ограничения проверок: **[отчёт](REPORT_PERMALINK)**. Самостоятельно запускаемые сценарии: **[тесты воспроизведения](TEST_PERMALINK)**. Перед публикацией заменить `REPORT_PERMALINK` и `TEST_PERMALINK` ссылками `blob/<полный SHA коммита>/...`.

## Ошибки, которые дают ложный PASS

- Расчёт реализованного PnL трекером может отличаться от Bybit на 10 USDT. Отличие только журналируется; verdict получает скопированный `closed_pnl` и остаётся PASS.
- Replay может выставить ордер в 10 раз больше лайва или оставить дополнительный неисполненный ордер. Сравнение исполненного объёма проходит, состояние ордеров не проверяется. Случай подтверждён полным запуском `ReplayEngine` с настоящим `GridEngine`.
- Исполнение в `t=1` может быть повторно сопоставлено с ордером, созданным в `t=2`. Синтетический тикер при этом переносит цену более позднего рыночного события на раннее время. Verdict может остаться PASS.
- REST-восстановление приватных исполнений отбрасывает корректные элементы ответа Bybit: `category` находится в `result`, а обработчик ищет её в каждой записи `result.list`. Для REST-закрытий также подставляется нулевой `closedPnl`, когда поле отсутствует.
- Свежий публичный тикер не подтверждает полноту приватной записи. Текущая проверка принимает снимки позиций без ограничения возраста и может выдать зелёную строку при снимках суточной давности.
- При нулевом доступном балансе seed кошелька отвергается и используется значение конфигурации (по умолчанию 10 000). Отсутствующие позиции нужного символа заменяются нулевыми, если предварительная проверка увидела снимки другого символа.
- Исполнение без `orderLinkId` может сопоставиться с чужим ордером той же стороны даже при невозможной лимитной цене; воспроизведён PASS для покупки по 100 против Buy Limit 1.
- После перезапуска recorder активный `--watch` продолжает использовать старый `run_id`.
- В режиме `--shared` единственная совпавшая точка кошелька в начале окна достаточна для PASS; конечное состояние может не иметь записанной точки сравнения.

## Критерии исправления

1. Окно с неподтверждённой полнотой приватных исполнений, устаревшими снимками или неполным seed получает SKIP с причиной, а не PASS. REST-восстановление проверено контрактным тестом по документированному ответу Bybit.
2. Результат отдельно показывает и проверяет PnL, рассчитанный трекером, и PnL, полученный из записанных исполнений. Расхождение не остаётся только WARNING.
3. Сравниваются выставленные, частично исполненные и отменённые ордера: идентификатор, сторона, лимитная цена, начальный объём, остаток и reduce-only. Проверяются размеры и цены входа обеих сторон позиции.
4. Исполнение не может происходить раньше создания ордера. Стратегия на каждом событии использует только доступную к тому времени рыночную информацию. Эвристическое сопоставление без идентификатора не считается доказанным совпадением.
5. `--watch` при автоматическом выборе записи переходит на новый `run_id`; `--shared` требует покрытие окна записанными точками кошелька, включая конец.
6. Регрессионные тесты инвертируют ожидания сценариев аудита: ошибочные случаи дают FAIL или SKIP. Текущие тесты воспроизведения намеренно зелёные, пока проблемы существуют.

## Проверка

На проверенном коммите прошли 2175 штатных тестов, один был пропущен. Дополнительные 11 сценариев воспроизводят перечисленные проблемы. Они используют синтетические данные и SQLite в памяти, не обращаются к рабочему счёту или производственной базе.

```sh
uv run --no-sync pytest docs/audits/live_check_2026_09_27/test_audit_reproductions.py -q
```

Issue отслеживает весь аудит. При реализации его стоит разделить на отдельные исправления для полноты данных, независимого расчёта PnL, ордеров и хронологии; связывать PR с ними через GitHub Development или явные ссылки.
